# OneDriver.Net

An interactive, shell-like OneDrive client for Linux (and any platform .NET runs on), written in C#.

Instead of running a background daemon that mirrors your whole drive, OneDriver.Net gives you a REPL where you browse your OneDrive like a filesystem (`ls`, `cd`), pick exactly which folders you care about, and run a sync when *you* decide to.

```
OneDriver.Net
=============

Hello, Jane Doe (jane@example.com)!

root >> ls
[Documents - (12 items)] [SYNC]
[Pictures - (340 items)]
notes.txt [local]
report.pdf [online]

root >> cd Documents
Documents [SYNC] >> sync
Starting synchronization of marked folders...
Syncing folder 'Documents': 3 file(s) to download, 9 already present locally.
...
Folder 'Documents': 3 downloaded, 0 failed in 1.84 seconds.
```

---

## Why another OneDrive sync?

I created this project just for fun. I had a hard time selecting folders in [abraunegg/onedrive](https://github.com/abraunegg/onedrive), so I decided to spend a few hours coding
my own way to access OneDrive and implement a workflow that works for me. I mostly work with photos, so I don't need to worry about files changing — each newly exported photo is a new file.

It is a work in progress, and I don't encourage you to use my project instead of the ones mentioned here!

## Why not just use the existing clients? (Generated by AI. Seriously, use them! They are real clients!)

| | OneDriver.Net | [abraunegg/onedrive](https://github.com/abraunegg/onedrive) | [OneDriver (jstaf)](https://github.com/jstaf/onedriver) | rclone |
|---|---|---|---|---|
| Model | Interactive shell + on-demand sync | Background daemon / monitor mode | FUSE filesystem | CLI transfer tool |
| Always-running process | No | Yes (for live sync) | Yes (mount) | No |
| Browse before downloading | Yes (`ls` / `cd` over Graph API) | No (config-file driven) | Yes (via mount) | Yes (`rclone ls`) |
| Selective sync setup | Interactive `mark` / `mark-all` while browsing | Hand-written `sync_list` patterns | N/A (everything is virtual) | Per-command paths |
| Works offline with local copies | Yes — plain files in `~/OneDrive` | Yes | Only cached files; stale mount when offline | Yes |
| Integrity verification | SHA1 checked on every download | Yes | Yes | Yes |
| Resumable large uploads | Yes (Graph upload sessions) | Yes | Yes | Yes |
| Runtime dependency | .NET runtime | D compiler / distro package | FUSE + systemd | Go binary |

**Where OneDriver.Net wins:**

- **No daemon, no FUSE, no systemd unit.** Nothing runs while you are not using it, so nothing burns CPU, holds a mount point, or breaks when the network drops. You open the shell, sync, and close it.
- **Explore first, commit later.** With `abraunegg/onedrive` you must guess folder paths and write `sync_list` rules before you know what is up there. Here you `cd` around your actual drive and `mark` folders as you find them.
- **Your files are real files.** Unlike a FUSE mount, everything under `~/OneDrive` is an ordinary directory that survives reboots, works with any tool, and needs no special process to read.
- **Predictable, non-destructive syncing.** The sync is additive: files missing locally are downloaded, files missing remotely are uploaded. Nothing is ever deleted by the tool, so a bad sync can't wipe your drive — a failure mode users of full bidirectional clients know well.
- **Throttle-aware by design.** Concurrency limits are configurable and deliberately conservative, since the Graph API returns HTTP 429 to aggressive clients.
- **Hackable.** It's a small, dependency-injected C# console app. Adding a command means adding one class implementing `ICommand`.

**Where it doesn't win:** there is no real-time file watching, no conflict resolution, no delete propagation, and no rename tracking. If you want a fully automated two-way mirror, use `abraunegg/onedrive`. OneDriver.Net is for people who want control and a small blast radius.

## Requirements

- [.NET 10 SDK](https://dotnet.microsoft.com/download) (or newer)
- A Microsoft account (personal OneDrive by default — see [Work/School accounts](#workschool-accounts))

## Installation

```bash
git clone https://github.com/tiagodeliberali/OneDriver.Net.git
cd OneDriver.Net
dotnet run
```

To build a self-contained binary:

```bash
dotnet publish -c Release -r linux-x64 --self-contained
```

## First run and authentication

Authentication uses the **device code flow**, so it works over SSH and on headless machines. On first run you'll see something like:

```
To sign in, use a web browser to open the page https://microsoft.com/devicelogin
and enter the code ABCD-EFGH to authenticate.
```

Open the URL on any device, enter the code, and grant access. The resulting authentication record and token cache are stored under your configuration directory, so subsequent runs sign you in silently.

### Token cache security

`Azure.Identity` encrypts the token cache using the platform keyring. On headless Linux boxes without a keyring, encryption is unavailable and the client falls back to **unencrypted** storage. This fallback is controlled by `settings.tokenCache.allowUnencryptedStorage` in [appsettings.json](appsettings.json) and the app prints a yellow warning at startup whenever it is active.

Set it to `false` if you are on a desktop with a working keyring:

```json
"tokenCache": {
  "name": "OneDriver.Net.TokenCache",
  "allowUnencryptedStorage": false
}
```

## Commands

| Command | Description |
|---|---|
| `ls` | List the current OneDrive folder. Folders are blue, files are marked `[local]` or `[online]`, and folders marked for sync show `[SYNC]`. |
| `cd <path>` | Enter a folder. Accepts nested paths (`cd Documents/Work`) and `..` for the parent. |
| `df <file>` | Download a single file from the current folder into `~/OneDrive/<current path>`. |
| `mark [folder]` | Mark the current folder (or a named subfolder) for syncing. |
| `mark-all [folder]` | Recursively mark a folder and every subfolder below it. |
| `sync-list` | Show all folders currently marked for syncing. |
| `sync-remove <path>` | Unmark a folder. |
| `sync` | Sync every marked folder: download remote-only files, upload local-only files. |
| `help [command]` | List commands, or show help for one of them. |
| `quit` | Exit. |

### Typical workflow

```
root >> cd Documents
Documents >> ls
Documents >> mark-all           # mark Documents and everything beneath it
Documents >> mark               # also include Documents itself
Documents >> sync-list
Documents >> sync
```

Re-run `sync` whenever you want to reconcile; it skips anything already present on both sides.

## How syncing works

For every marked folder, `sync` compares the remote listing with the local directory:

- **Remote-only files → downloaded**, in parallel (`maxConcurrentDownloads`), and each one is **verified against the SHA1 hash reported by OneDrive**. A mismatch deletes the partial file and reports the error.
- **Local-only files → uploaded**, in parallel (`maxConcurrentUploads`). Files over 4 MB use a **resumable Graph upload session** with 3.2 MB chunks.
- **Files present on both sides are skipped.** Content is not compared, so the tool never overwrites either side.
- A failure on one file is reported and the rest of the folder continues.

Large folders are enumerated correctly: the Graph API pages `driveItem` children, and the client follows every `@odata.nextLink` via `PageIterator`.

## Layout on disk

| Path | Contents |
|---|---|
| `~/OneDrive/` | Downloaded files, mirroring your OneDrive folder structure. Configurable via `settings.paths.rootFolderName`. |
| `$XDG_CONFIG_HOME/OneDriver.Net/sync_config.txt` | The list of folders marked for syncing (`path:driveItemId` per line). |
| `$XDG_CONFIG_HOME/OneDriver.Net/OneDriver.Net.TokenCache.authrecord.json` | Cached authentication record for silent sign-in. |

## Configuration

All settings live in [appsettings.json](appsettings.json) under the `settings` section. Create `appsettings.Development.json` (git-ignored) or use `dotnet user-secrets` to override them without touching the tracked file.

| Key | Default | Description |
|---|---|---|
| `clientId` | *(public sample app id)* | Azure AD application (client) ID. |
| `tenantId` | `consumers` | `consumers` for personal accounts, `organizations` or a tenant GUID for work/school. |
| `graphUserScopes` | `user.read`, `Files.ReadWrite`, `Files.Read.All`, `Files.ReadWrite.All` | Delegated Microsoft Graph permissions requested at sign-in. |
| `tokenCache.name` | `OneDriver.Net.TokenCache` | Name of the persisted token cache. |
| `tokenCache.allowUnencryptedStorage` | `true` | Allow the unencrypted cache fallback on Linux. |
| `paths.rootFolderName` | `OneDrive` | Local sync root, relative to your home directory. |
| `paths.configurationFolderName` | `OneDriver.Net` | Configuration directory name. |
| `sync.maxConcurrentDownloads` | `8` | Parallel downloads. Raising this invites HTTP 429 throttling. |
| `sync.maxConcurrentUploads` | `4` | Parallel uploads. |

### Using your own app registration

The bundled `clientId` is convenient for trying the tool out, but for anything serious register your own app:

1. Go to the [Azure Portal → App registrations](https://portal.azure.com) and create a new registration.
2. Under **Authentication**, enable **Allow public client flows** (required for the device code flow).
3. Copy the **Application (client) ID** into `settings.clientId`.

### Work/school accounts

Set `tenantId` to `organizations` or to your tenant GUID. Note that your administrator may need to consent to the requested Graph scopes.

## Project structure

```
Program.cs                 Host + dependency injection wiring
Application.cs             The REPL loop and command dispatch
Settings.cs                Strongly-typed configuration
RuntimeData.cs             Current-folder stack backing `cd`/`ls`
Commands/                  One class per shell command (ICommand)
Domain/                    OneDriveEntry / OneDriveFile / OneDriveFolder / LoggedUser
Services/GraphApi/         Microsoft Graph access and authentication
Services/Files/            Local filesystem and configuration I/O
Services/SyncFolders/      The marked-folder registry
```

### Adding a command

Implement `ICommand`, then register it in `Program.ConfigureServices`:

```csharp
services.AddTransient<ICommand, MyCommand>();
```

`Application` discovers every registered `ICommand` and wires up `help` automatically.
